How it works

Issue. Present. Verify.

The whole system is three moves. None of them requires trusting what the agent says about itself.

01 · ISSUE

The builder signs a credential

Whoever operates an agent issues it a signed credential: this agent belongs to us, here is its public key, here is what it is allowed to do. The credential is signed with the issuer's private key, so it cannot be forged or edited without detection.

Any builder can issue credentials under the open spec. There is no central issuer and no permission needed.

02 · PRESENT

The agent shows it on arrival

When the agent visits a merchant, it presents its credential the way a browser presents a certificate. The merchant's server sees a cryptographic claim, not a self-declared header.

03 · VERIFY

The merchant checks the math

The merchant (or our free verifier) checks the signature, confirms the issuer, and checks the credential has not expired or been revoked. The answer is a signed yes or no, in under a second.

What verification does and does not mean

It means

This agent is who it claims to be. The credential is intact, the issuer is recognized, and it has not been revoked.

It does not mean

This agent is safe, honest, or well behaved. Identity is a fact about origin. Behavior is a separate question, and we do not answer it.

Revocation, up front

Credentials can be stolen or misused, so every credential can be revoked by its issuer, and the verifier checks revocation on every lookup. The honest part: revocation at internet scale has hard unsolved corners, like propagation delay. The spec states the revocation story on page one, including what is not solved yet.
